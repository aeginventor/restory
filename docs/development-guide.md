# 개발과 GitHub 작업 순서

restory는 독립된 폴더와 Git 저장소로 관리합니다. 원격 저장소는 [aeginventor/restory](https://github.com/aeginventor/restory)입니다. 이 저장소는 공개되어 있으므로 실제 감상 기록, 이메일, 인증 정보와 환경변수 값을 커밋하지 않습니다.

## 로컬 작업

프로젝트 폴더를 Codex에서 열고 `AGENTS.md`와 `docs/product.md`를 먼저 읽도록 합니다. 다른 프로젝트의 폴더에서 명령을 실행하거나 파일을 옮기지 않습니다.

```bash
npm ci
npm run dev -- --port 34761
```

Node.js는 `.nvmrc`의 버전을 사용하고, 브라우저에서 `http://127.0.0.1:34761`을 엽니다. 환경변수가 없는 첫 실행은 체험 모드입니다. 실제 계정 저장은 [Supabase 안내](supabase.md)를 따라 별도로 설정합니다.

## 기능별 변경

1. 현재 브랜치와 미커밋 변경을 확인합니다. 다른 작업이 남아 있으면 그대로 보존합니다.
2. 업데이트할 기준 브랜치를 확인하고 기능 브랜치에서 작업합니다.
3. 구현한 흐름을 브라우저에서 사용하고 필요한 테스트를 실행합니다.
4. 변경된 파일을 검토한 뒤 커밋하고 같은 이름의 원격 브랜치로 올립니다.
5. 초안 PR에 문제, 변경된 동작, 검증 결과와 남은 설정을 적습니다.
6. 미리보기와 자동 검사를 확인한 뒤 PR을 기본 브랜치에 반영합니다.

저장소에 처음 코드를 올리는 경우에는 원격 기본 브랜치가 아직 없을 수 있습니다. 이때는 최초 커밋과 기본 브랜치를 먼저 만든 뒤 기능 PR을 만듭니다. 존재하지 않는 기준 브랜치로 PR을 생성했다고 보고하지 않습니다.

2026년 10월 1일 최초 구현을 `feat/restory-mvp`로 올렸고, GitHub가 이 브랜치를 기본 브랜치로 지정했습니다. 원격 `main`과 PR은 아직 없습니다. 기본 브랜치 초기화 push는 자동 승인 검토에서 거절되어 실행하지 않았습니다. 다음 변경은 현재 기본 브랜치에서 새 기능 브랜치를 만들고 `feat/restory-mvp`를 대상으로 PR을 열 수 있습니다. `main`으로 전환하려면 소유자가 기준 브랜치 생성과 기본 브랜치 변경을 별도로 승인해야 합니다.

```bash
git status --short --branch
npm run check
npm run test:e2e
```

GitHub CLI로 PR을 만들 경우 `gh auth status`로 인증 상태를 확인합니다. 브라우저 로그인이 필요한 경우 직접 인증하며 토큰을 프롬프트나 저장소 파일에 붙이지 않습니다.

## 검증 기준

| 변경 영역 | 확인할 내용                                       |
| --------- | ------------------------------------------------- |
| 기록      | 저장, 새로고침 후 유지, 수정, 삭제, 내보내기      |
| 재감상    | 같은 작품에 새 기록을 추가해도 이전 기록이 남는지 |
| 날짜      | 정확한 날짜, 연월, 연도, 모름이 구별되는지        |
| 계정      | 로그인과 로그아웃, 다른 사용자 데이터 접근 차단   |
| 공개      | 공개 동의, 스포일러, 공개 취소 후 조회 차단       |
| 화면      | 모바일, 긴 글, 빈 상태, 키보드와 오류 메시지      |

`npm run check`는 lint, 타입 검사, 단위 테스트와 빌드를 실행합니다. `npm run test:e2e`는 Playwright로 체험 모드를 확인합니다. 첫 실행에는 `npx playwright install chromium`으로 브라우저를 설치합니다. 테스트는 34761 포트에 전용 서버를 실행하며 기존 서버를 재사용하지 않으므로, 실행 중인 같은 포트의 개발 서버를 먼저 종료합니다.

GitHub Actions는 Node.js 24에서 같은 검사와 체험 브라우저 테스트를 실행합니다. 별도 작업에서는 PostgreSQL 서버 바이너리를 설치하고 `supabase/tests/run-security.sh`로 임시 데이터베이스의 권한을 검사합니다. CI에는 운영용 Supabase 키를 넣지 않습니다. 실제 인증과 Supabase HTTP API 권한은 별도 테스트 프로젝트의 두 사용자와 비로그인 상태에서 추가로 확인해야 합니다. 검사 명령을 만들었다는 사실과 검사가 실제 통과했다는 사실을 구분해서 기록합니다.

GitHub Actions 설정은 [GitHub의 Node.js 안내](https://docs.github.com/en/actions/tutorials/build-and-test-code/nodejs), 브라우저 설치와 실행은 [Playwright CI 안내](https://playwright.dev/docs/ci)를 따릅니다.

## 개인 기록과 설정 파일

- `.env.local`에는 로컬 환경에 필요한 값만 저장하고 Git에서 제외합니다.
- `.env.example`에는 변수 이름과 설명만 둡니다.
- 테스트와 화면 예시는 허구의 감상으로 작성합니다.
- 내보낸 JSON과 운영 데이터 백업은 공개 저장소 밖에 보관합니다.
- DB 구조 변경은 기존 파일을 임의로 덮기보다 새 마이그레이션으로 남깁니다.

작업이 끝나면 실제 실행한 검사, 통과 여부, 미검증 이유와 후속 설정을 PR에 적습니다. 기능을 변경할 때 README와 제품 정책도 함께 확인합니다.
