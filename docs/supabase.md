# Supabase 연결과 데이터 관리

2026년 10월 1일 `restory` Supabase 프로젝트를 만들고 초기 마이그레이션을 SQL Editor에서 적용했습니다. 로컬 `.env.local`도 연결했습니다. 환경변수가 비어 있는 다른 컴퓨터에서는 체험 모드로 동작합니다.

실제 프로젝트의 공개 감상 API 응답과 비로그인 요청의 개인 기록, 프로필 조회 차단을 확인했습니다. 소유자가 직접 가입과 이메일 인증을 마쳤으며, 배포 주소에서 해당 계정의 비공개 저장, 연도만 있는 날짜, 새로고침 후 유지와 수정을 확인했습니다. 실제 비공개 기록이 있는 상태에서도 비로그인 조회는 차단됐습니다. 아래 처음 연결하기 절차는 새 환경을 만들 때 사용하며, 현재 프로젝트에 초기 마이그레이션을 다시 실행하지 않습니다.

검증용 감상은 소유자 승인 후 정확한 행 ID와 테스트 내용을 조건으로 SQL Editor에서 한 건 삭제하고 앱에서 감상 0건을 확인했습니다. 브라우저 자동화가 네이티브 삭제 확인창에 응답하지 못해 정리 경로를 바꾼 것으로, 실제 배포의 UI 삭제 확인창까지 검증했다고 보지 않습니다. 삭제 흐름의 자동 브라우저 테스트는 로컬과 CI에서 통과했습니다.

데이터베이스 마이그레이션은 별도의 로컬 PostgreSQL 17에서 실행했습니다. 두 사용자와 비로그인 권한으로 개인 기록 접근 차단, 공개와 공개 취소, 운영자 권한, 계정 삭제를 검증했습니다. 이 검증은 Supabase의 실제 이메일 인증이나 HTTP API 연결 검증을 대신하지 않습니다.

## 처음 연결하기

1. [Supabase 대시보드](https://supabase.com/dashboard)에서 새 프로젝트를 만듭니다. 프로젝트 이름은 `restory-dev`처럼 개발용임을 구분할 수 있게 정하고, 데이터베이스 비밀번호는 별도 비밀번호 관리자에 보관합니다.
2. 프로젝트의 SQL Editor에서 `supabase/migrations/` 안의 파일을 이름 순서대로 각각 한 번씩 실행합니다. `202610010001_initial.sql`은 초기 스키마, `202610010002_public_search.sql`은 공개 감상 서버 검색입니다. 적용한 파일을 다시 실행하지 않으며, 다음 스키마 변경은 새 마이그레이션 파일로 추가합니다. 현재 운영 프로젝트에는 두 파일이 모두 적용되어 있습니다(두 번째 파일은 2026년 10월 7일 적용).
3. 프로젝트 URL과 공개용 Publishable key를 확인합니다. 예전 프로젝트의 `anon` 키도 사용할 수 있습니다. 브라우저용 키는 데이터 접근 권한을 대신하지 않으므로 SQL의 RLS 규칙과 함께 사용해야 합니다.
4. 프로젝트 폴더의 `.env.example`을 `.env.local`로 복사해 다음 값을 입력합니다.

   ```dotenv
   NEXT_PUBLIC_SUPABASE_URL=https://프로젝트주소.supabase.co
   NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=공개용키
   NEXT_PUBLIC_DEMO_MODE=false
   ```

5. Supabase의 Authentication 설정에서 이메일 로그인을 활성화합니다. 이메일 확인을 사용하는 경우 인증 메일을 실제로 받을 수 있는 주소로 시험합니다.
6. Authentication의 URL Configuration에서 Site URL을 서비스 주소로 설정하고, Redirect URLs에 사용할 콜백 주소를 등록합니다. 로컬 기본값은 `http://127.0.0.1:34761/auth/callback`이며 비밀번호 재설정용 `http://127.0.0.1:34761/auth/callback?recovery=1`도 등록합니다. 배포 뒤에는 `https://배포도메인/auth/callback`과 `https://배포도메인/auth/callback?recovery=1`을 추가합니다. 실제 사용하는 주소만 허용합니다.
7. 개발 서버를 다시 시작하고 가입, 이메일 확인, 로그인, 기록 저장, 새로고침, 로그아웃을 확인합니다.

관리자용 secret key, `service_role` 키, 데이터베이스 비밀번호는 이 서비스의 브라우저 코드에 필요하지 않습니다. `.env.local`도 Git에 올리지 않습니다. 배포할 때는 호스팅 서비스의 환경변수 설정에 같은 공개용 변수 이름을 등록하고 다시 빌드합니다.

`NEXT_PUBLIC_DEMO_MODE=true`이면 다른 변수가 있어도 체험 모드를 강제하며 원격 데이터베이스에 연결하지 않습니다. 테스트와 화면 확인에 사용할 수 있습니다.

공식 참고: [API 키 종류](https://supabase.com/docs/guides/api/api-keys), [RLS와 데이터 권한](https://supabase.com/docs/guides/database/postgres/row-level-security), [인증 리디렉션 주소](https://supabase.com/docs/guides/auth/redirect-urls).

## 가입 방식: Google 로그인

일반 이용자의 가입은 Google 로그인으로 받습니다. 이메일 확인 메일을 보내지 않으므로 별도 SMTP 서비스가 필요 없습니다. 이메일과 비밀번호 로그인은 소유자 계정처럼 이미 만든 계정을 위해 그대로 남겨 둡니다.

코드는 `NEXT_PUBLIC_GOOGLE_LOGIN=true`일 때만 로그인 화면에 Google로 계속하기 버튼을 보여줍니다. 아래 설정을 마치기 전에는 값을 바꾸지 않습니다.

1. [Google Cloud Console](https://console.cloud.google.com/)에서 restory용 프로젝트를 만들거나 기존 프로젝트를 고릅니다. OAuth 동의 화면의 앱 이름이 로그인 창에 표시되므로 `hobby-map` 프로젝트를 같이 쓰면 "취미 지도"라는 이름이 보입니다. 이름이 다르게 보여도 괜찮다면 같은 프로젝트를 써도 됩니다.
2. OAuth 동의 화면에서 범위는 이메일과 프로필 기본 범위만 사용합니다. 이 범위는 Testing 상태에서도 테스트 사용자 등록 없이 누구나 로그인할 수 있고 7일 승인 만료의 예외입니다.
3. 사용자 인증 정보에서 웹 애플리케이션 OAuth 클라이언트를 만들고, 승인된 리디렉션 URI에 Supabase가 Authentication → Sign In / Providers → Google 화면에 표시하는 callback 주소를 넣습니다. 형태는 `https://riajlcrqopmyxiymgzrk.supabase.co/auth/v1/callback`입니다.
4. 발급된 Client ID와 Client Secret을 Supabase의 Google 제공자 설정에 직접 입력하고 제공자를 켭니다. 두 값은 저장소, 환경변수, 대화에 넣지 않습니다.
5. Supabase URL Configuration의 Redirect URLs에 `https://restory-vert-six.vercel.app/auth/callback`과 로컬 주소 `http://127.0.0.1:34761/auth/callback`이 있는지 확인합니다.
6. Vercel 환경변수와 로컬 `.env.local`에 `NEXT_PUBLIC_GOOGLE_LOGIN=true`를 넣고 다시 배포합니다.
7. 시크릿 창에서 Google로 가입해 닉네임 기본값 "기록하는 사람"이 보이는지, 설정에서 닉네임을 바꿀 수 있는지, 로그아웃과 재로그인 뒤 기록이 유지되는지 확인합니다.

Google 로그인으로 만든 계정은 가입 시 닉네임을 받지 않으므로 기본 닉네임으로 시작합니다. 공개 감상을 쓰기 전에 설정에서 바꾸도록 안내합니다. 공식 참고: [Supabase Google 로그인](https://supabase.com/docs/guides/auth/social-login/auth-google)

## 기록과 공개 범위

`works`의 개인 작품은 등록자만 읽을 수 있습니다. `entries` 원본 역시 작성자만 조회, 수정, 삭제할 수 있습니다. 원본 기록을 공개로 바꾸어도 다른 사용자가 원본 테이블을 읽을 권한은 생기지 않습니다.

공개할 때 `set_entry_visibility` 함수가 공개 작품 사본을 만들고 감상에 연결합니다. 원래 개인 작품과 감상 시점은 그대로 유지합니다. 이미 공개된 작품을 직접 선택해 기록을 남긴 경우 그 공통 작품 페이지에 함께 표시됩니다. 제목이 같다는 이유로 작품을 자동 병합하지 않습니다.

공개 조회는 `list_public_entries`와 `get_public_entry` 함수가 처리합니다. 이 함수는 공개 상태이고 운영자가 숨기지 않은 감상, 닉네임, 작품 정보만 반환합니다. 이메일, 로그인 사용자 ID, 개인 작품 ID, 신고자는 반환하지 않으며, 개인 책갈피 여부도 공개하지 않습니다. 목록은 한 번에 20개씩 가져옵니다. 공개 취소, 삭제, 운영자 숨김 이후에는 다음 조회부터 공유 주소에서도 내용을 반환하지 않습니다. 이미 다른 사람이 복사한 글이나 열어둔 화면까지 회수하는 기능은 아닙니다.

가입할 때 직접 입력한 닉네임은 공백을 정리하고 1~40자인 경우에만 초기 프로필에 반영합니다. 없거나 형식에 맞지 않으면 `기록하는 사람`을 사용합니다. 이메일에서 닉네임을 추출하거나 사용자 메타데이터의 관리자 권한 값을 복사하지 않습니다.

누군가 공개 작품을 선택해 자신의 감상을 남긴 경우, 원래 등록자가 공개를 취소해도 그 사람의 개인 기록에 필요한 작품 정보는 남습니다. 공개 감상이 하나도 없는 공통 작품은 일반 공개 작품 목록에서 보이지 않습니다.

감상 시점은 문자열로 정확히 저장합니다. 예를 들어 연도만 아는 경우 `2021`, 연월만 아는 경우 `2021-08`, 정확한 날짜는 `2021-08-14`, 모르는 경우 `null`입니다. 기록을 입력한 시각은 별도 열에 저장되므로 감상한 시점과 섞이지 않습니다.

## 신고와 운영자

로그인한 사용자는 공개 감상을 신고할 수 있습니다. 신고자는 자신의 신고만 조회할 수 있고, 신고 대상 작성자에게 신고자 정보는 공개하지 않습니다. 같은 사람이 같은 글을 다시 신고하면 기존 신고 사유를 갱신합니다.

운영자 권한은 브라우저나 사용자 프로필 수정으로 획득할 수 없습니다. 프로젝트 소유자가 SQL Editor에서 확인한 계정 UUID를 대상으로 다음 명령을 직접 실행합니다.

```sql
update public.profiles set is_admin = true where id = '운영자로 지정할 계정 UUID';
```

운영자 확인에는 `is_current_user_admin`, 신고 목록에는 `list_moderation_reports`, 감상 숨김과 복원에는 `moderate_entry`를 사용합니다. 모든 함수는 데이터베이스에서 운영자 권한을 다시 확인합니다. 숨겨진 감상은 작성자가 다시 공개해도 노출되지 않습니다. 이 상태에서도 작성자 자신의 아카이브와 감상 원문은 보존됩니다.

## 계정 삭제

`delete_my_account`는 로그인한 본인의 계정만 삭제합니다. 다른 계정 ID를 인자로 받지 않습니다. 본인의 감상, 개인 작품, 프로필, 신고와 인증 계정을 삭제합니다. 다른 사용자가 이미 함께 사용한 공통 작품과 다른 사용자의 감상은 남습니다. 계정 삭제 뒤 앱은 이 브라우저의 인증 세션도 지웁니다.

운영 데이터를 삭제하기 전에는 필요한 기록을 내보내야 합니다. 시험 계정으로 먼저 확인하고, 실제 운영 전에는 Supabase 프로젝트의 백업 제공 여부와 복구 절차를 요금제에 맞춰 확인합니다.

## 로컬 데이터베이스 권한 테스트

PostgreSQL 서버 바이너리가 설치되어 있으면 다음 명령으로 독립된 임시 데이터베이스에서 검증할 수 있습니다. 개발용이나 운영용 Supabase 데이터베이스에 접속하지 않습니다. 네트워크 포트를 열지 않고 임시 Unix 소켓을 사용하며, 실행이 끝나면 클러스터를 제거합니다.

```bash
PG_BIN=/opt/homebrew/opt/postgresql@17/bin bash supabase/tests/run-security.sh
```

환경에 따라 `PG_BIN` 경로를 바꿉니다. PostgreSQL의 `pg_config --bindir` 경로에 `initdb`가 있으면 `bash supabase/tests/run-security.sh`만 실행해도 됩니다. CI에서도 PostgreSQL 서버 바이너리를 설치한 뒤 같은 명령을 사용할 수 있습니다.

`bootstrap.sql`은 시험용 `auth.users`, `auth.uid()`와 접속 역할을 만드는 파일입니다. 실제 Supabase 프로젝트에는 실행하면 안 됩니다. 실제 프로젝트에는 `migrations` 폴더의 파일만 적용합니다.

실제 프로젝트 연결 후에는 A 계정, B 계정, 비로그인 브라우저로 다음을 추가 확인합니다.

- A의 비공개 기록 ID로 B가 조회, 수정, 삭제할 수 없는지 확인합니다.
- B의 비공개 작품에 A가 감상을 연결할 수 없는지 확인합니다.
- 공개한 감상의 공유 주소를 비로그인 상태에서 열고, 공개 취소 뒤 다시 불러오면 내용을 볼 수 없는지 확인합니다.
- 닉네임 변경, 이메일 인증, 세션 만료, 비밀번호 재설정과 계정 삭제를 확인합니다.
- 배포 도메인과 개발 도메인의 인증 콜백을 각각 확인합니다.

처음에는 개발용 Supabase 프로젝트를 사용하고, 실제 이용자가 생기기 전에 운영용 프로젝트를 별도로 만듭니다. 개발 테스트로 운영 계정의 기록을 삭제하지 않도록 배포 환경의 변수와 연결 대상을 구분해야 합니다.
